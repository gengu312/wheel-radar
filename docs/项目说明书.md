# WheelRadar：独立开发者 & 办公人群的“工具选型器”项目说明书（v0.1）

> 目标：当我有一个新需求/想法时（例如“PDF 转 Markdown”“批量压缩图片”“做一个番茄钟 App”），WheelRadar 能自动从多个可信来源检索**可直接使用的成品工具**与**可复用的开源轮子**，并输出**结构化对比 + 可解释的选型结论**，帮助我避免重复造轮子、快速做决策。

---

## 0. 项目命名与定位

### 0.1 项目名
- **英文**：WheelRadar  
- **中文**：轮子雷达（可选：轮子雷达 / 轮子雷达站 / 轮子雷达工具）

### 0.2 一句话定位
**输入需求 → 直接可用工具 + 开源替代方案 + 风险提示 + 对比结论，一次给到。**

### 0.3 为什么叫 WheelRadar
- “Wheel”代表开源轮子/现成工具/可复用方案
- “Radar”代表“扫描、发现、筛选、定位最佳选项”
- 未来可扩展：不仅找 repo，也找成品软件/网站/插件/模板/镜像

## 1. 背景与动机

我经常遇到两类需求：

1) **办公工具需求**：格式转换、批量处理、OCR/转写、文件协作、自动化脚本等  
2) **独立开发需求**：寻找开源库/CLI/模板/self-hosted 工具，评估可维护性与商用风险

现状痛点：
- 直接用搜索引擎：结果杂、需要自己判断、耗时
- 直接 GitHub 搜：只给 repo 列表，不给“能不能用/风险/替代品/集成成本”
- 直接问 AI 搜：答案可能不稳定、证据链不清晰、不易复用沉淀

因此需要一个“站在现有工具肩膀上”的整合器：**不是另一个搜索框，而是“选型与决策工具”。**

---

## 2. 产品定位与核心差异化

### 2.1 与“AI 直接搜索/GitHub 搜”的差异化
WheelRadar 的差异化在于：
- **多源分桶**：把结果分为“三桶 + 注意事项聚合视图”（直接可用 / 开源自部署 / 开发可集成 / 注意事项）
- **可解释评分（ToolScore/WheelScore）**：活跃度、可用性、风险、成本、适配度等
- **可复现与可审计**：每个结论都能追溯来源、筛选规则与关键证据
- **可沉淀**：历史、收藏、导出对比矩阵（后续迭代）

### 2.2 核心价值
- 节省调研时间（少翻链接）
- 降低踩坑概率（风险提示）
- 更快做决策（对比矩阵 + 结论）
- 可复用（导出 + 历史）

## 4. MVP 功能范围（建议先做小而能打）

### 4.1 必须有（v0.1）
1) **一句话输入**（自然语言）
2) **意图识别**：判断用户想要的是  
   - 成品（网站/桌面/移动/插件）  
   - 开源（repo / self-hosted / docker）  
   - 开发集成（包/SDK/CLI）
3) **多源检索**（先少而精）：拉候选集合
4) **去重与归并**：同一项目不同链接/镜像、fork 归类
5) **结果分桶展示**（三桶 + 注意事项）：
   - 直接可用（网站/软件/插件）
   - 开源可自部署（repo/docker/self-hosted）
   - 可集成（npm/pypi 等）
   - 注意事项（聚合视图：从三桶里提取“高风险/高成本/高不确定”项与风险点）
6) **ToolScore/WheelScore + 理由**（可解释）
7) **一键导出 Markdown**：对比表 + 选型结论（用于 Notion/飞书/README/Issue）
8) **多语言支持 (i18n)**：UI 界面与 AI 输出结果需支持多语言切换（至少支持中文与英文）。

### 4.2 暂不做（v0.1 禁区）
- 全网爬虫大而全（维护成本爆炸）
- 账号体系/团队协作/复杂权限
- 订阅提醒与长期监控（v0.2+）
- 应用商店评论大规模抓取（合规与反爬风险高，后置）

### 4.3 分桶规则（v0.1 可执行口径）
- **可集成（Integratable）**：来源为 NPM/PyPI，或 GitHub 项目明确是 SDK/库/CLI（有 package metadata、安装指令、API 文档）。
- **开源可自部署（Self-hosted）**：来源为 Docker Hub 镜像，或 GitHub 项目明确是服务/应用（提供 Docker/Compose/K8s/自托管说明）。
- **直接可用（Ready-to-use）**：v0.1 主要来自“有官方 Hosted Demo/在线服务/可下载安装包”的 GitHub 项目（由 `homepage`、README、Release assets 等弱信号判断）；v0.2+ 由 CSE/目录站点补齐。
- **注意事项（Cautions）**：不是独立来源桶，而是对三桶结果做规则抽取/合并展示（例如：高风险 license、隐私上传、维护停更、成本不透明）。

## 5. 搜索源设计（v0.1 务实版）

> **变更说明**：经调研，AlternativeTo 和 Chrome Web Store 无官方公开 API；PyPI 官方 Search API 已弃用、Docker Registry API 无搜索端点。为保证 MVP 稳定性与开发速度，v0.1 聚焦于**API 友好型**与**可替代检索**源，非标准源作为 v0.2 探索目标。

### 5.1 核心源（v0.1 聚焦）
1) **GitHub** (REST/GraphQL API)：基石。提供 Repo 元数据、README、Star 趋势、Issues 等。
2) **NPM** (Registry API + Search)：补充开发生态数据，适合“找库/找 CLI”。
3) **Docker Hub**（Hub API + Registry API）：  
   - 搜索/仓库列表：Hub API（有官方参考文档，但需注意鉴权与限流，用于关键词检索候选）  
   - 详情/标签用 Registry API（用于补充镜像信息）
4) **PyPI**（无官方 Search API）：v0.1 采用替代检索策略（见 5.2）。

### 5.2 PyPI 替代检索策略（v0.1）
- **推荐路径（PyPI BigQuery 官方数据集）**：用 `bigquery-public-data.pypi.distribution_metadata` 做关键词检索 → 返回包名列表。  
- **补充指标（可选）**：用 `bigquery-public-data.pypi.file_downloads` 估算下载活跃度（避免直连 PyPI/减少请求）。  
- **JSON API 补全**：对包名调用 PyPI JSON API（`https://pypi.org/pypi/{name}/json`）获取最新版本与元信息。  
- **备选（Libraries.io）**：如果不想接 BigQuery，可用 Libraries.io 做关键词检索（通常需要 API Key）。  
- **反向映射**：优先从 GitHub Repo 的 `pyproject.toml`/`setup.py` 解析包名，减少搜索压力。  
- **降级策略**：若索引不可用，则仅展示 GitHub/NPM/Docker 结果并提示“PyPI 搜索暂降级”。

### 5.3 数据源对照表（v0.1 落地口径）
| Source | 候选集检索 | 详情补全（Hydrate） | 主要用途 | 备注 |
|---|---|---|---|---|
| GitHub | Search API / GraphQL | Repo/Release/README 等 | 开源轮子、可自部署项目 | 限流明确；强缓存友好 |
| NPM | `/-/v1/search` | `registry.npmjs.org/{pkg}` | 可集成（JS/TS） | 下载量需额外接口（可选） |
| Docker Hub | Hub API（Search） | Registry API（tags/manifest） | 自部署成品/镜像 | 需要做限速与失败降级 |
| PyPI | BigQuery/Libraries.io（Search） | PyPI JSON API（项目元信息） | 可集成（Python） | 不做 HTML 抓取作为主路径 |
| Google CSE | 定点站内检索 | 二次抓取 + AI 抽取 | 成品软件补齐 | v0.2+（配额/成本可控） |

### 5.4 备选/降级源（v0.2+ 或 曲线救国）
1) **Google Programmable Search Engine (CSE)**：
   - 用途：针对 AlternativeTo、Chrome Store、Product Hunt 进行定点检索。
   - 优点：有官方 API，合规。
   - 缺点：只能拿到标题/链接/摘要，拿不到结构化评分数据（需配合 AI 进行二次页面解析）。
   
> **v0.1 策略**：先做好 **GitHub + NPM + Docker Hub** 的搜索与深度分析，PyPI 通过替代检索补齐；对于“成品软件”，暂时通过 GitHub 的 Topics (e.g., `topic:windows`, `topic:app`) 进行覆盖，并保留 CSE 作为后续增强。

### 5.5 参考链接（实现时查阅，可选）
- GitHub Search API: https://docs.github.com/en/rest/search/search
- NPM Registry API（含 Search）: https://github.com/npm/registry/blob/main/docs/REGISTRY-API.md
- Docker Hub API: https://docs.docker.com/reference/api/hub/latest/
- PyPI JSON API: https://docs.pypi.org/api/json/
- PyPI BigQuery: https://docs.pypi.org/api/bigquery/
- pip search 说明（已弃用）: https://pip.pypa.io/en/stable/cli/pip_search/

### 5.6 凭证与配额（v0.1 运行前置）
- **GitHub**：建议配置 Token（避免低速率限制）；对匿名用户做更严格的 `max_items` 与缓存。
- **NPM**：公开 Search/Registry 一般可匿名访问，但仍需做限速与缓存（避免被临时限流）。
- **Docker Hub**：公开内容可访问，但 Hub API 可能需要鉴权/有更严格限流；应提供可选登录（PAT/Token）并做降级（Hub API 失败则仅展示 GitHub 侧的自部署候选）。
- **PyPI BigQuery**：需要 GCP 项目与访问 BigQuery 的凭证/配额（可能产生费用）；若不接入，则用 Libraries.io 或仅做 GitHub 反向映射 + PyPI JSON API 补全。
- **LLM**：需要模型 Key；深读只在用户触发时调用，并对相同 `canonicalId + prompt_version + model` 做缓存。

## 6. AI 交互策略（按需高性能模式）

> **核心原则**：Performance First。避免一次性分析所有结果导致长达 30s+ 的等待。采用了 **"Lazy Loading + On-Demand"** 策略。

### 6.1 交互流程（三步走）
1) **极速列表（0-2s）**：
   - 仅依赖传统 API/索引（GitHub/NPM/Docker Hub/PyPI 索引）返回的元数据（标题、描述、基础指标：Star/下载/拉取量/更新时间）。
   - **不调用 LLM**，确保首屏秒开。
   - 利用关键词高亮匹配度。

2) **按需深读（User Triggered）**：
   - 用户点击某条目（或勾选 Top 3 对比）时，触发 **"Deep Scan"**。
   - 此时后端抓取可直接获取的文本（GitHub README/Release notes、NPM/PyPI 描述、Docker Hub 描述等），流式传输给 LLM。
   - v0.1 不把“任意网页抓取”作为主路径（合规/稳定性原因）；需要网页二次抽取的场景放到 v0.2+（CSE + 定点抓取）。
   - **语言适配**：Prompt 中需明确指示 LLM 根据用户当前的语言设置（中文/英文）输出分析报告。
   - **UI 表现**：Skeleton 骨架屏 -> 逐行打字机输出分析报告。

3) **智能缓存（Smart Cache）**：
   - 分析过的结果存入 Redis/DB（有效期 7 天）。
   - 下次有其他用户搜到同款工具，直接出缓存的深度报告。

### 6.2 成本与稳定性优势
- **省钱**：用户没兴趣的点不开，不消耗 Token。
- **快**：列表页无阻塞。
- **稳**：避免并发请求大量 URL 导致的超时或限流风险。

### 6.3 限流与降级策略（v0.1）
- **查询预算**：每个来源设定 `timeout` 与 `max_items`，超时即返回部分结果。
- **分批加载**：默认返回 Top N，提供“加载更多”触发后续检索。
- **缓存优先**：热门需求命中缓存直接返回；未命中才触发外部搜索。
- **部分可用**：若某源失败，UI 明确标注“该源暂不可用”，不阻塞其他来源。

## 7. ToolScore / WheelScore 评分体系（v0.1 示例）

> 评分必须“可解释”：每项都要显示证据来源与计算方式（至少给出关键字段）。

### 7.0 ToolScore vs WheelScore（保留双体系）
- **ToolScore**：面向“成品工具”，强调可用性/成本/隐私与平台适配。
- **WheelScore**：面向“开源轮子”，强调维护活跃度/许可证风险/集成成本。
- **适用桶**：ToolScore 主要用于“直接可用”；WheelScore 主要用于“可集成/开源可自部署”。
- **统一尺度**：两者都落在 0–100，维度可不同，但需要展示证据与权重。
- **跨源归一化**：按桶内 percentile 做归一化，避免 Star/下载量规模差异造成偏差。

### 7.1 推荐维度
- **可用性（Usability）**：文档/示例/安装方式是否清晰  
- **活跃度（Activity）**：最近提交/最近发布/issue 响应情况  
- **风险（Risk）**：
  - 开源：license 风险（MIT/Apache/BSD vs GPL/AGPL 等）
  - 成品：隐私风险（是否上传文件、是否声明数据用途）
- **成本（Cost）**：免费/一次性/订阅、是否水印/限制  
- **适配（Fit）**：平台（Win/Mac/移动/离线）、语言、是否可直连

### 7.2 v0.1 可落地的“低复杂度计算”
- Activity：
  - `days_since_last_push`
  - `days_since_last_release`
  - `open_issues_count`（可作为风险信号）
- Risk：
  - `license` 字段直接映射到风险等级
- Usability：
  - README 长度/是否有 Quickstart/是否有 CI badge（弱信号）
- Fit：
  - repo topics / package keywords / 平台标签

### 7.3 v0.1 权重建议（先够用，再迭代）
- **WheelScore**（开源）：Activity 35% + Risk 30% + Usability 20% + Fit 15%（Risk 为扣分项）
- **ToolScore**（成品）：Usability 30% + Cost 25% + Risk 25% + Fit 20%（Risk 为扣分项）

> v0.2+ 再引入更复杂指标：issue 首响中位数、bus factor、依赖链 license、breaking change 频率等。

## 8. 系统架构建议（开源友好、易扩展）

### 8.1 组件划分
- **前端 Web**：输入、结果三桶 + 注意事项、对比矩阵、导出 Markdown
- **后端 API**：检索编排、数据源适配、去重与评分、缓存
- **Job/队列（可选）**：异步抓取 README/官网内容、AI 抽取、定期刷新
- **存储**：
  - 缓存：Redis（或 Postgres 表 + TTL）
  - 数据：Postgres（或 SQLite 起步也行）
- **可观察性**：基础日志 + 简单 metrics（后续再做）

### 8.2 数据源适配器模式（核心）
每个 Source 一个 Adapter：
- `search(query)-> candidates[]`
- `hydrate(candidate)-> enrichedCandidate`
- `normalize()-> canonical schema`

这样你后续加源只要加适配器，不动主流程。

### 8.3 Canonical Candidate Schema（v0.1 最小可用）
> 目标：跨源统一字段，确保“分桶/去重/评分/导出”都只依赖这套 schema。

```ts
type CandidateSource = 'github' | 'npm' | 'pypi' | 'docker_hub' | 'cse';
type CandidateBucket = 'ready_to_use' | 'self_hosted' | 'integratable';

export type Candidate = {
  canonicalId: string; // e.g. github:owner/repo, npm:pkg, pypi:pkg, docker_hub:ns/repo
  entityId?: string; // cross-source merge key (prefer github repo when available)
  name: string;
  description?: string;
  source: CandidateSource;
  bucket: CandidateBucket; // primary bucket (3 buckets); "注意事项" tab is an aggregated view
  url: string; // primary URL to open

  licenseSpdx?: string;
  lastUpdatedAt?: string; // ISO string

  toolScore?: number; // 0-100 (for products)
  wheelScore?: number; // 0-100 (for OSS)
  reasons?: string[]; // short, evidence-backed bullets for the score/bucket

  cautionFlags?: string[]; // e.g. 'license:agpl', 'privacy:uploads', 'stale', 'paid_or_opaque'
  evidenceLinks?: Array<{ label: string; url: string }>;
};
```

> v0.2+ 再扩展：cost、platform、privacy detail、maintainer signals、cross-source link map（repo <-> package <-> image）。

### 8.4 去重与归并规则（v0.1 可执行口径）
目标：同一个“工具实体”（repo / package / image）在 UI 中尽量合并展示，减少重复与误导。

1) **源内去重**（必做）  
   - GitHub：`github:{owner}/{repo}`  
   - NPM：`npm:{name}`  
   - PyPI：`pypi:{name}`  
   - Docker Hub：`docker_hub:{namespace}/{repo}`  

2) **跨源归并（EntityId）**（v0.1 够用）  
   - **优先用 GitHub repo 作为 entityId**：`entityId = github:{owner}/{repo}`  
   - NPM：解析 `package.json.repository`/`homepage` 指向的 GitHub → 归并到该 repo  
   - PyPI：解析 `project_urls`/`home_page` 指向的 GitHub → 归并到该 repo  
   - Docker Hub：使用 Hub 元信息（description/homepage）或常见命名规则推断 GitHub → 归并到该 repo（推断不确定则不强合并，只做“可能关联”提示）

3) **fork/镜像处理**（v0.1 规则）  
   - 若 GitHub 标记为 fork：默认展示上游（upstream）为主；fork 仅在更活跃或有关键差异时作为“变体”出现。  
   - Docker 镜像同名多 namespace：优先官方/Verified/Star 较高者，其他作为备选。

4) **注意事项生成（Cautions Tab）**  
   - 规则命中即打 `cautionFlags`，并在“注意事项”聚合展示：停更（长期无更新）、高风险 license（GPL/AGPL）、缺少使用说明、疑似需上传数据/隐私不明、成本/限制不透明等。

## 9. 技术栈决策（已定案：全栈 TypeScript）

采用 **Next.js (App Router) + TypeScript** 全栈方案，兼顾开发效率、类型安全与 Vercel AI SDK 的流式支持。

- **Frontend**: Next.js (React) + Tailwind CSS + ShadcnUI
- **Backend**: Next.js Route Handlers (Serverless)
- **Database**: PostgreSQL (推荐 Supabase 或 Neon) + Drizzle ORM
- **Queue/Job**: BullMQ (Redis) 或 Inngest (Serverless friendly) —— *用于异步处理 AI 分析任务*
- **AI Integration**: Vercel AI SDK (统一接口，方便切换 OpenAI/Anthropic/Gemini)
- **Deployment**: Vercel (前端+API) + 托管 DB

> **决策理由**：统一语言栈降低维护成本；Vercel AI SDK 对流式 UI (Streaming UI) 支持极其完善，完美契合本项目的“AI 解释”场景。

## 10. 里程碑计划（建议按 4 个小迭代推进）

### 10.1 Milestone 0：Repo & 基建（1–2 天）
- 初始化项目、Lint/Format、基础 UI、基础 API
- 定义 Candidate Schema（统一字段）

### 10.2 Milestone 1：GitHub 单源闭环（3–5 天）
- **核心数据源**：GitHub API
- **核心流程**：Query -> GitHub Search API -> 列表展示（无 AI）-> 点击详情 -> 流式 AI 分析 README -> 输出结构化结论
- **功能**：基础搜索、按需 AI 分析、Markdown 导出

验收标准：
- 输入“PDF to Markdown”，能秒出 GitHub 仓库列表。
- 点击任一仓库，5秒内开始流式输出其“优缺点/适用场景/部署风险”。

### 10.3 Milestone 2：多源聚合（1–2 周）
- **新增数据源**：NPM / Docker Hub / PyPI（替代检索 + JSON API 补全）
- **聚合逻辑**：跨源去重（识别同一个项目的 Repo 和 Package）
- **增强**：引入 Redis 缓存 AI 分析结果
- **探索**：尝试接入 Google CSE 搜索部分非开源工具（视 API 额度而定）

验收标准：
- 同一需求能搜到“源代码(GitHub)”和“成品镜像(Docker)”以不同 Tab 或标识展示。

### 10.4 Milestone 3：AI 结构化 + 对比矩阵（1–2 周）
- AI 抽取：功能点、限制、平台、隐私/许可、用法
- 自动生成对比表（可导出）
- 加强缓存与降级策略

验收标准：
- 输出稳定、可复用；用户无需打开 10 个链接才能决策

### 10.5 v0.1 端到端验收用例（读者可复现）
用例 A：输入 `PDF 转 Markdown（优先离线/开源）`  
- 列表页 2 秒内返回（至少 GitHub + NPM；其他源可降级但不阻塞）  
- “可集成”能看到 npm/pypi 相关库（如有），点击任一条能流式给出“安装方式/适用场景/限制/许可证风险”  
- “开源可自部署”能看到相关服务/镜像（如有）  
- “注意事项”能列出至少 3 条可验证风险点（例如：AGPL、长期停更、需要上传文件/隐私不明、付费限制）并给证据链接  
- 导出 Markdown 一键生成（包含对比表 + 证据链接）

用例 B：输入 `批量压缩图片（保持清晰，Windows 优先）`  
- 结果包含“可集成库”和“成品/自部署工具”两类候选（v0.1 如成品不足可在备注中解释来源局限）  
- 对比矩阵里能看到平台/许可证/更新时间/关键理由等字段，结论可解释且可追溯

## 11. 合规与风险（必须提前考虑）

- **优先使用官方 API**，避免大规模网页爬虫成为核心依赖
- 对于第三方站点（目录/商店），注意 ToS；可先做“链接聚合 + 少量元信息”
- 对“隐私敏感工具”（上传文件类）明确标注风险：本地/离线优先推荐
- 对开源 license 做显著提示：GPL/AGPL 等需要高亮
- **输入与日志最小化**：默认不存用户原始文件，仅保存查询与评分结果；缓存有 TTL（如 7 天），提供删除入口
